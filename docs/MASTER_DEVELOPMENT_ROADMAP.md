## Delivery stages

### Stage A — stability and foundations

1. Complete Music lifecycle, transition serialization, process cleanup, and voice reconnect tests. Startup, finish, transition, bounded child cleanup, pending-ZeroMQ Stop, and fake-gateway Ready/reconnect paths now have Manager-level coverage; real gateway integration remains.
2. Complete Effects readiness, shutdown ordering, endpoint lease handling, and FFmpeg tests. Allocator retry, request interruption and lease behavior are unit-tested, and the bundled FFmpeg filter/controller handshake passed; FFmpeg port race and full Manager integration remain.
3. Define storage schema/version policy; connect the new adapter without breaking legacy JSON formats.
4. Establish shared permission policy and enforce Feature Guard at module execution boundaries.
5. Add deterministic lifecycle and persistence suites. Do not run the bot as a test harness.

### Stage B — main user-facing modules

1. Finish Dashboard navigation and show only usable capabilities.
2. Expand AI Tag into a deterministic permission-aware router; put generative AI behind an optional provider adapter.
3. Connect Translator service to Dashboard and AI Tag; target language selection and provider URL/key documentation are implemented. Verify only with the configured provider and preserve explicit unavailable errors.
4. Finish Greeter configuration and text/TTS mode behind a provider interface.
5. Wire Voice Manager events to its state service and recovery flow.
6. Finish lyrics lifecycle/karaoke and use Translator for translated lyrics.
7. Persisted playlists and opt-in session autoplay are implemented and regression-tested. Radio discovery routes station-name/tag searches through Dashboard and AI Tag; playback uses a DNS/redirect-validating loopback relay before FFmpeg. Live provider, Discord gateway, and real station playback validation remain.

### Stage C — AI server features

1. Template storage, dry-run planning, confirmation checks, executor, rollback and Dashboard routes exist. AI Tag now selects create/rebuild/clone/smart-merge modes and enters the same guarded preview/apply flow; next: hierarchy/error-path coverage and verify supported Discord operations without starting the bot.
2. Create/rebuild/clone/smart merge plans are implemented; rebuild preserves extra roles and deletes only target channels absent from the source snapshot. Real Discord hierarchy and rollback behavior remain unverified.
3. Security audit/report routes are implemented with persistence and no automated actions. Add health signals and configurable policy; offline alone must not imply a dead bot, and no automatic kick without explicit policy and safeguards.

### Stage D — integration and release readiness

1. Route supported modules through Dashboard and AI Tag.
2. Apply permission and feature checks at every entry point and service boundary.
3. Run module, lifecycle, persistence, and interaction regression suites.
4. Verify configuration docs and secret-redacted logs.
5. Mark DONE only with behavior-level evidence. Production startup/deployment is separately authorized.

## Working rules

- Before editing an existing active file, create a timestamped sibling backup and retain every older backup.
- Prefer isolated module files; coordinate shared integration files after module APIs are stable.
- Never send a UI success response before the underlying operation succeeds.
- Use mocks by default; do not start the production bot for tests.
- Update statuses only when new evidence supports the change, and record that evidence.
